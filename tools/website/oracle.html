Oracle · the two-rolls paradox

One verify block. Three tools. Two answers.

A 30-line example that passes aver verify and fails aver proof — on identical source. The same gap that conventional Z3 verification can't reach for effectful code.

The code

A function rolls a die twice and returns whether the two rolls were different. The verify block declares that, under a stub distinctStub returning n + 1, the function holds => true.

fn distinctStub(path: BranchPath, n: Int, lo: Int, hi: Int) -> Int
    ? "Stub returning n+1 — different value per call counter."
    n + 1

fn twoRollsDistinct() -> Bool
    ? "Roll a die twice; return whether the two rolls were different."
    ! [Random.int]
    a = Random.int(1, 6)
    b = Random.int(1, 6)
    a != b

verify twoRollsDistinct law alwaysDistinct
    given rnd: Random.int = [distinctStub]
    twoRollsDistinct() => true

Run it three ways

Same file. Three commands. The first runs the verify block as a sample under the stub; the other two export the same block as a universal theorem and ask a real proof backend to discharge it.

$ aver verify two_rolls_paradox.av
PASSES
Verify: two_rolls_paradox.av
  ✓ verify distinctStub      2/2
  ✓ verify twoRollsDistinct  1/1

Summary: 3/3 cases passed
$ aver proof --backend lean && lake build

  ensures twoRollsDistinct(
    Root, rnd

Why one block has two answers

aver verify evaluates the law as a finite sample. The cartesian product of given domains is enumerated and run against the law's RHS. With distinctStub returning n + 1, the two calls produce 1 and 2; 1 != 2 holds; the sample case passes. This is the — familiar — testing path: assert against a chosen implementation, run, verify equality.

aver proof takes the same block and lifts it. Every classified effect call (here Random.int) becomes an explicit function parameter. The exported theorem says for every possible such function — not just the stub you supplied — the law's RHS holds. That's a strictly stronger claim. There exist oracles (e.g. one that always returns 5) for which the two calls return the same value and the law fails. Lean and Dafny independently reject the export for this reason.

The block is unchanged between runs. Only the question being asked changes: "does this hold for the stub I wrote?" versus "does this hold for every implementation of this signature?". The first question is sample testing; the second is verification. Aver lets you ask both with one block, and tells you when they disagree.

What conventional Z3 verification doesn't reach

Most contract-verification systems built on Z3 prove pre/post conditions on pure functions, then stop at the effect boundary. Random results are unconstrained for the solver — there are no useful axioms about them beyond range. Contracts that depend on specific random values fall to runtime checking, not static rejection. Same shape for HTTP responses, disk reads, time, network: the SMT model has no symbolic handle on them, so the proof obligation evaporates.

Aver's Oracle export does the extra step. Classified effects — Random, Http, Disk read-side, Tcp.send, Time.now, Console.readLine, non-modal Terminal, Args, Env read-side — are lifted into the proof artifact as explicit function parameters with structured call addressing (BranchPath + per-branch counter). The exported theorem quantifies over them. Universal claims about effectful code become provable, and rejectable when they're false. The two-rolls paradox is what that gap looks like, in 30 lines.

Run it yourself

cargo install aver-lang
git clone https://github.com/jasisz/aver
cd aver

# 1. Sample passes
aver verify examples/formal/two_rolls_paradox.av
  ✓ 3/3 cases passed

# 2. Lean rejects
aver proof examples/formal/two_rolls_paradox.av --backend lean --output out
cd out && lake build
  ✖ unsolved goals

# 3. Dafny rejects
aver proof examples/formal/two_rolls_paradox.av --backend dafny --output out
dafny verify out/*.dfy
  ✖ postcondition could not be proved
